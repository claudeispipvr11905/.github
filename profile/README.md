<h2>一、掉线先分层，别一上来就换供应商</h2>
<p>一条链路从客户端到目标服务，中间至少有四段：本地网络、运营商出口、代理服务器、目标站点。掉线现象看起来一样，根因可能在这四段里的任何一段。不分层就没法定位。</p>
<h3>先看掉的是哪一种</h3>
<p>分三种：连接直接断开、连接还在但没有数据、周期性断开可自动恢复。第一种查链路，第二种查保活，第三种查会话回收。三种的排查路径完全不同。</p>
<h3>定一个观测起点</h3>
<p>在出问题的机器上开一个持续探测，每五秒记录一次结果，连续跑一小时。没有这组数据，后面的所有判断都是猜。</p>

<h2>二、根节点一：物理链路与运营商出口</h2>
<p>这一层的特征是：掉线不区分目标站点，访问任何国外地址都不稳，本地网络测速可能是正常的。</p>

<h3>用 mtr 看丢包发生在哪一跳</h3>
<p>mtr 持续跑十分钟以上，重点看从第几跳开始出现丢包。如果丢包从第一跳就开始，问题在本地路由或网线；如果从运营商出口之后开始，问题在运营商；如果只在最后几跳，问题在目标侧。</p>
<h3>晚高峰是分水岭</h3>
<p>同一段路径，白天正常、二十点后大量丢包，这是典型的拥塞而非故障。这种掉线换供应商不一定解决，因为瓶颈可能在同一家上游。判断方法是对比不同时段同一目标的结果。</p>

<h2>三、根节点二：代理服务端的会话回收</h2>
<p>这一层的特征是：连接能建立，但维持不了太久，通常在固定的时间长度后断开，比如正好三十分钟、正好一小时。</p>
<h3>固定周期断开基本可以确定是回收策略</h3>
<p>服务端为了回收资源，会给空闲或超长的会话设一个上限。如果你的使用是长连接但长时间无数据，被回收是正常的，不是故障。解决办法是加心跳，而不是换服务商。</p>
<h3>怎么看是不是被回收</h3>
<p>在客户端抓包，看断开前有没有 FIN 或 RST。有 FIN 说明是对端正常关闭，属于策略；直接超时没有任何包，说明中间链路丢了，属于网络问题。这个区别很关键。</p>

<h2>四、根节点三：客户端重连逻辑写错了</h2>
<p>这是最容易被漏掉的一层，因为现象看起来像"网络不稳"。典型表现是：断开之后不再自动恢复，或者恢复后立刻又断，形成抖动。</p>
<h3>重连太急会让情况更糟</h3>
<p>断开后立即重连、连续失败后仍以固定一秒间隔重试，会在服务端看来是一波连接风暴。很多服务端会因此临时拉黑，于是你看到的掉线时间被自己延长了。正确做法是指数退避：一秒、两秒、四秒、八秒，上限三十秒。</p>
<h3>状态机没重置</h3>
<p>有些脚本重连后没有重置内部状态，仍用旧的会话标识去请求，服务端认为无效直接断开。表现就是"连上了但立刻断"。检查重连分支里有没有重新初始化会话。</p>
<h3>并发数没有回收</h3>
<p>连接断了但客户端的连接池没释放，越重连占用越多，最后到上限全部卡住。用 ss 或 netstat 看 ESTABLISHED 和 TIME_WAIT 的数量，异常堆积说明池没回收。</p>

<h2>五、根节点四：DNS 与 TLS 会话没有复用</h2>
<p>这一层的特征是：连接时好时坏，抓包能看到 DNS 查询很慢或者每次都重新握手，整体表现为"卡顿式掉线"。</p>
<h3>DNS 每次重新解析</h3>
<p>如果客户端每次请求都走一遍 DNS，而 DNS 又没走代理，解析结果可能不同，导致连到不同节点，会话自然不连续。固定使用代理解析，或者缓存解析结果，能明显改善。</p>
<h3>TLS 每次都完整握手</h3>
<p>完整握手要两到三个往返，跨境链路上就是几百毫秒。开启会话复用后，重复连接只需一个往返。这不是掉线，但会被误认为掉线，因为等待时间太长触发了超时。</p>
<h3>MTU 不匹配导致大包丢失</h3>
<p>小请求正常、大文件或长回复卡住，是 MTU 问题的典型表现。把接口 MTU 调到 1400 左右试一次，如果能通，就是分片被丢弃。这个坑在隧道类代理上特别常见。</p>

<h2>六、一棵能照着走的排查树</h2>
<p>把上面四层串起来，形成一条固定的排查路径。遇到掉线从根节点往下走，命中即停，不要跳步。</p>
<h3>第一步到第三步</h3>
<p>第一步跑 mtr 十分钟，看是否有持续丢包；第二步看断开方式，是 FIN 还是超时；第三步看连接池，TIME_WAIT 是否异常增长。三步做完，八成的掉线已经定位。</p>
<h3>第四步到第五步</h3>
<p>第四步查重连逻辑，是否有退避、是否重置状态；第五步查 DNS 与 MTU，用小包和大包分别测一次。五步走完仍无结论，才考虑换供应商，并把这五步的数据一起提交，通常能得到更快的处理。</p>

<h2>常见问答</h2>
<h3>掉线一定是 IP 质量差吗？</h3>
<p>答：不一定。固定时长断开多为服务端会话回收，随机断开多为链路丢包，连上即断多为重连逻辑或鉴权问题。先分清类型，再判断是不是地址本身的问题。</p>
<h3>心跳设多久合适？</h3>
<p>答：常见做法是三十秒到五分钟一次，具体看服务端的空闲回收阈值。设得比阈值短一半比较稳妥，太频繁反而增加流量和连接数压力。</p>
<h3>重连间隔设一秒可以吗？</h3>
<p>答：不建议。固定一秒重试容易形成连接风暴，反而触发临时限制。用指数退避，从一秒起步翻倍，上限三十秒，并在成功后退回初始值。</p>
<h3>换供应商能彻底解决掉线吗？</h3>
<p>答：只能解决链路与服务端策略这一部分。如果根因在客户端重连逻辑或 DNS 配置，换谁都会掉。建议先走完五步排查再决定。</p>
